  5. Functional requirements

  Each acceptance criterion (AC) is written as input → status → result and
  corresponds to at least one automated test.

  Categories

  FR-01 Create category. POST /api/categories
  - AC1: {"name":"Food"} → 201. The response contains the body with an id and a
    Location header.
  - AC2: {"name":""} or a 51-character name → 400 with errors.Name.
  - AC3: {"name":"food"} when "Food" already exists → 409.

  FR-02 List and get categories. GET /api/categories, GET /api/categories/{id}
  - AC1: A list request → 200 with an array sorted by name.
  - AC2: An unknown id → 404 ProblemDetails.

  FR-03 Update category. PUT /api/categories/{id}
  - AC1: A valid new name → 200 with the updated record.
  - AC2: A name that duplicates another category → 409. An unknown id → 404.

  FR-04 Delete category. DELETE /api/categories/{id}
  - AC1: A category with no expenses → 204. A later GET → 404.
  - AC2: A category with ≥ 1 expense → 409, and the category still exists.

  Expenses

  FR-05 Create expense. POST /api/expenses
  - AC1: A valid body (title, amount 12.50, today's date, existing categoryId) →
    201 with the expense, warnings: [] and a Location header.
  - AC2: Each of amount 0, −1, 1000000.01, 10.123, a future date, a missing
    date, an empty title or a 101-character title → 400 naming the field.
  - AC3: An unknown categoryId → 400 with errors.CategoryId.

  FR-06 Get expense. GET /api/expenses/{id}
  - AC1: An existing id → 200. An unknown id → 404.

  FR-07 Update expense. PUT /api/expenses/{id}
  - AC1: A valid body → 200 with the updated expense and warnings.
  - AC2: An invalid body → 400. An unknown id → 404.

  FR-08 Delete expense. DELETE /api/expenses/{id}
  - AC1: An existing id → 204. A repeated delete → 404.

  FR-09 Search, filter, sort, page. GET /api/expenses?q=&categoryId=&from=&to=&m
  inAmount=&maxAmount=&sortBy=&sortDir=&page=&pageSize=
  - AC1: No parameters → 200 with { items, page:1, pageSize:20, totalCount, 
    totalPages }, sorted by date descending.
  - AC2: q=taxi matches a case-insensitive substring of the title or notes. Each
    other filter narrows the results, and filters combine with AND.
  - AC3: sortBy=amount&sortDir=asc → items sorted by amount ascending.
  - AC4: pageSize=101, page=0, from later than to, or sortBy=foo → 400.
  - AC5: A page beyond the last page → 200 with empty items and the correct
    totalCount.

  Budgets

  FR-10 Budget CRUD. POST/GET/PUT/DELETE /api/budgets[/{id}], plus GET 
  /api/budgets?month=YYYY-MM
  - AC1: {"categoryId":1,"month":"2026-10","limit":500,"type":"Hard"} → 201.
  - AC2: A second budget for the same category and month → 409.
  - AC3: limit ≤ 0, month 2026-13 or an unknown type → 400.
  - AC4: A GET includes the calculated spent, remaining, percentUsed and status
    (BR-01).

  FR-11 Hard budget enforcement. A category has a Hard budget with a 100.00
  limit and 90.00 already spent.
  - AC1: A new expense of 10.00 → 201 (exactly at the limit). The status is
    Warning.
  - AC2: A new expense of 10.01 → 422 ProblemDetails, and the expense count does
    not change.

  FR-12 Soft budget warning. The same setup with a Soft budget.
  - AC1: A new expense of 20.00 → 201. The warnings[] list contains a
    budget-exceeded message, and the status is Exceeded.

  Summaries and reports

  FR-13 Monthly totals. GET /api/summaries/monthly?year=2026
  - AC1: → 200 with [{ month:"2026-01", total, count }, …] for months that have
    expenses, sorted ascending.

  FR-14 Category summary. GET /api/summaries/categories?month=2026-10
  - AC1: → 200 with one row per category: categoryId, categoryName, total,
    count, budgetLimit?, percentUsed? and status?. Totals match the sum of the
    seeded data.
  - AC2: An invalid month → 400.

  FR-15 Report (JSON). GET /api/reports/monthly?month=2026-10&format=json
  - AC1: → 200 application/json with { month, grandTotal, categories[…], 
    expenses[…] }.

  FR-16 Report (CSV). GET /api/reports/monthly?month=2026-10&format=csv
  - AC1: → 200 text/csv with Content-Disposition: attachment; 
    filename="expenses-2026-10.csv".
  - AC2: The header row is Date,Title,Category,Amount. Values containing commas
    or quotes are RFC 4180-escaped. Amounts use invariant culture with 2
    decimals.
  - AC3: format=xml → 400.

  Platform

  FR-17 Persistence. The data is stored in SQLite and the schema is created only
  by EF Core migrations. Seed data covers a few categories, budgets and
  expenses.
  - AC1: dotnet ef database update on an empty folder creates the database. The
    API starts and GET /api/categories returns the seeded rows.

  FR-18 API docs. OpenAPI document and UI available in Development. An .http
  file contains sample requests for every endpoint.
  - AC1: GET /openapi/v1.json → 200. Every sample request in the .http file runs
    successfully against a fresh database.

  FR-19 React client. A lean Vite + React + TypeScript app.
  - AC1: Lists expenses with filters and paging, plus create, edit and delete
    forms that show validation errors from the API.
  - AC2: Manages categories and budgets, and shows the budget status (OnTrack /
    Warning / Exceeded) for the selected month.
  - AC3: Shows soft-budget warnings after a save and shows a hard-budget 422 as
    an error. It can download the CSV report.
  - AC4: The API base URL comes from VITE_API_URL. CORS allows only the Vite dev
    origin.

  FR-20 Automated tests.
  - AC1: xUnit unit tests cover the validation and budget rules. Integration
    tests use WebApplicationFactory with an in-memory SQLite connection and
    cover every FR-01…FR-16 AC.
  - AC2: Vitest tests cover the client's API wrapper and at least the expense
    form validation display.
  - AC3: dotnet test and npm test both pass.

  5. SQLite decimal limitation

  SQLite has no decimal type, so EF Core stores decimal as TEXT. The SQLite
  provider cannot translate ORDER BY on decimal columns or Sum/Average/Min/Max 
  over decimals. These throw at runtime instead of silently giving wrong
  answers. TEXT ordering would be lexical in any case ("100" < "9"). Decimal
  comparisons in WHERE may be translatable, but this must be confirmed by an EF
  Core 10 test before we rely on it.

  Decision:
  1. Apply the supported filters in SQL first: categoryId, date range, q (LIKE),
     plus the amount range if the test confirms it.
  2. Materialize only that filtered set with AsNoTracking(), projected to the
     needed columns.
  3. Sort and aggregate in C# using decimal: OrderBy(e => e.Amount), Sum(e => 
     e.Amount).
  4. Paging: when sortBy is date or title, page in SQL (Skip/Take). When
     sortBy=amount, sort the filtered set in memory and then page. Summaries and
     reports are always limited to one month or year.
  5. Never convert money to double/float (no value converters to REAL, no
     casts).

  This is acceptable because the app is local and single-user with a bounded
  dataset (NFR-07 targets 10k expenses; a filtered set of 10k rows is a few
  hundred KB). Storing integer cents was considered and rejected: the
  requirements set decimal Amount.

● Answered from CLAUDE.md, without opening any files:

  1. An expense that would exceed a Hard budget gets HTTP 422. The body is
     ProblemDetails with the extensions categoryId, month, limit, currentSpent
     and attemptedAmount, and nothing is saved. Spending exactly equal to the
     limit is allowed. A Soft budget never fails: it returns 201/200 with a
     warnings[] message.
  2. The API uses port 5200, at http://localhost:5200 with the http launch
     profile. Vite proxies /api there from http://localhost:5173. Don't use the
     https profile: its http port is 5050.
  3. To create a migration, run this from the repo root:
  dotnet ef migrations add <Name> --project backend/ExpenseManagement.Api
     Apply it with dotnet ef database update --project 
     backend/ExpenseManagement.Api, because the API doesn't migrate on startup.

  docs/requirements.md still says port 5000. Port 5200 is what the API is
  actually configured with.

  Tool: Bash
  Blocks: rm with recursive and force flags (-rf, -fr, -r -f, -Rf, --recursive

  clean -f/-fd (dry runs allowed) · git commit/push --no-verify (and commit -n)
   · DROP TABLE, DROP DATABASE, DELETE FROM without WHERE · dotnet ef database 
  drop
  ────────────────────────────────────────
  Tool: Bash: demo folder
  Blocks: Write-type commands (rm, mv, cp, touch, mkdir, tee, sed -i, git, npm,
  dotnet, and so on) in a pipeline that names claude-code-workshop, or after a
  cd into it, or when the session's working directory is inside it. Also >/>>
  redirects into it. Reading commands (ls, cat, grep) stay allowed.
  ────────────────────────────────────────
  Tool: Edit/Write
  Blocks: Paths outside CLAUDE_PROJECT_DIR · .env and .env.* (.env.example
  allowed) · *.db, *.db-shm, *.db-wal · anything with a Migrations folder in
  its path

  How it decides:
  - Commands are split on ;, &&, ||, |, & and newlines. Quoted text is never
    split, and 2>&1 isn't mistaken for a separator.
  - Paths go through Path.GetFullPath. On Windows, Git Bash-style /c/... paths
    are converted first and comparisons ignore case.
  - The demo-folder match excludes claude-code-workshop-assessment, because that
    is this project's own folder name.
  - Each decision is logged to .claude/logs/hooks.log. Only the reason is
    logged, never the full command.

  Things I added or interpreted

  - git clean -f without -d is blocked too. Any forced clean deletes untracked
    files.
  - Same checks for PowerShell commands, but not active yet. The code also
    checks PowerShell tool commands and Remove-Item -Recurse -Force. Your
    matcher is Bash|Edit|Write, so that only takes effect if PowerShell is added
    to the matcher. Right now the PowerShell tool bypasses the guard entirely.

  Known limitations and conflicts

  1. SQL checks look at the whole command text, so they can block harmless 
     commands. For example, grep "DELETE FROM" file or a commit message
     containing "drop table" would be blocked. That is intended to fail safe,
     and the block message says why.
  2. "Outside the project" also blocks paths Claude Code itself uses. That
     includes the session scratchpad, which security.md explicitly allows, and
     the memory directory under ~/.claude/projects/. Should I allow those two
     locations?
  3. The guard doesn't protect itself. Claude could still edit
     .claude/hooks/pre-guard.cs or .claude/settings.json to switch it off.
     Should I add those two files to the blocked list?
  4. Speed: dotnet run on a .cs file compiles it on the first run, which may
     take several seconds, and checks for changes on later runs. That cost
     applies to every Bash, Edit and Write call. Measure it during testing; the
     30-second timeout should cover the first compile.
  5. Untested: I haven't checked whether Claude Code applies a hook registered
     mid-session right away or only after a restart or a review in /hooks.
